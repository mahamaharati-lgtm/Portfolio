01

Product overview

Workflow Studio is a single-page web app for building approval workflows. A workflow is a graph of steps (Start, Task, Approval, Decision, Notification and End) connected by named outcomes such as Approved, Rejected, Returned, Yes and No.

People can lay out a workflow on a canvas or edit it as a structured list, configure roles and conditions, check it against business rules, publish it as a numbered version, and simulate a request through it while acting as each approver. Each simulated request keeps a complete history of who did what.

It runs entirely in the browser and stores data in localStorage. It is a frontend demonstration, not a production multi-user system.

02

Real-world problem

Most organisations run approval processes with rules that are easy to state and hard to follow consistently: every purchase goes to the requester’s manager; anything above ₹50,000 also needs finance; procurement is told once it is approved. When those rules live in people’s heads or in email chains, requests take the wrong route, approvals are skipped, and nobody can explain afterwards why a request ended up where it did.

A visual workflow builder makes the rules explicit and reviewable. It is only useful, though, if it stops people from publishing a broken process: a decision with only one branch, an approval nobody is assigned to, or a step that can never be reached.

03

Target users

I designed for two roles. These are my working assumptions, not findings from user research; no interviews or usability studies were run for this project.

  • Process owners (operations, HR, finance or IT administrators) who define and maintain workflows. They understand the business rules but are not developers.
  • Reviewers (managers or auditors) who need to check what a process does before it goes live, often on a laptop or phone, sometimes using only a keyboard or a screen reader.

Main assumptions: a workflow has one entry point; branching is driven by a few request fields (amount, duration, category, priority); and each step has one owning role rather than named individuals.

05

Information architecture

The app has three routes, with the editor split into clear regions:

  • Workflows (/): search, status filter (All, Drafts, Published), cards with status, step count, last update and validation summary, plus create and import.
  • Editor (/workflows/:id): a toolbar (name, status, save state, undo, redo, export, discard, save, publish), a step palette, the design area with Canvas and List tabs, and a side panel with Properties, Issues and Simulate tabs.
  • About (/about): what the demo does, keyboard shortcuts and limitations.

The side panel is the one place for details about the current selection, the workflow’s health, and its behaviour. This keeps the canvas uncluttered and gives each region one job.

06

User journeys

Build and publish a workflow

  1. Create a workflow from a blank canvas or a template.
  2. Add steps from the palette by clicking, or by dragging them onto the canvas.
  3. Connect outputs by dragging between handles, or by choosing targets in the Connections section.
  4. Fix each item in the Issues tab; “Show step” selects and centres the step that needs attention.
  5. Publish. The workflow becomes “Published v1”, and later edits create a new draft.

Check a workflow before it goes live

  1. Open Simulate. The form is pre-filled with the workflow’s sample request.
  2. Act as each assignee or approver; decisions and notifications run automatically.
  3. Read the request history to confirm every route, then review earlier runs under Recent runs.

07

Workflow examples

The app ships with five fictional example workflows: purchase, leave, expense, document and IT change.

Purchase approval: the ₹85,000 request

  1. Ananya Rao submits a request for ergonomic chairs worth ₹85,000.
  2. Manager review (Line Manager) approves. They could also reject it, or return it to Revise request.
  3. The decision Amount above ₹50,000? evaluates amount > 50000. The history records “Amount (₹) > ₹50,000 (Amount (₹) is ₹85,000)” and follows Yes.
  4. Finance approval (Finance Approver) approves.
  5. Notify procurement runs automatically, and the workflow ends as Approved.

With ₹20,000 the decision follows No and finance is skipped. A rejection at either approval notifies the requester and ends as Rejected.

IT change request: a deliberately incomplete draft

One template ships with a missing approver role, so the validation experience can be seen straight away. Publishing it is refused until a role is chosen.

08

Design exploration

These are the main alternatives I weighed while building, and why I chose as I did.

Design alternatives considered
QuestionOptionsDecision
How are branches shown?Generic edges with editable labels, or named output portsNamed ports per step type, so an approval always has Approved / Rejected / Returned and labels are never ambiguous
Where do details go?Modal dialogs, inline node editing, or a side panelTabbed side panel: no focus switching while editing, and it doubles as the validation and simulation surface
How does mobile work?Shrink the canvas, or provide a different editorA List view of the same graph, ordered from Start, which is the default below 768px
Autosave or explicit save?Autosave every change, or save on demandExplicit Save with a visible “Unsaved changes” state, so a half-edited published workflow is never silently changed
Can invalid workflows be simulated?Allow it with warnings, or block itBlock it, so simulation results always match what could be published
Loops?Forbid all cycles, or allow someOnly through an approval’s Returned branch, which models “send back for changes” without infinite loops

Visually, I kept the palette neutral and gave each step type a distinct colour bar and icon and text label. Edge colours (green Approved, red Rejected, dashed amber Returned) always come with a text label.

09

Component architecture

The code is split into a framework-free domain layer and a thin React layer:

  • domain/: types, per-step metadata (outputs, defaults), connection rules, validation, the simulation engine, the Zod import schema and templates. All pure functions, all unit-tested.
  • store/: Zustand stores. workflows persists workflows and runs through a localStorage wrapper that never throws (private mode, full storage). editor holds the draft, undo/redo history, selection and the running simulation.
  • components/editor/: Canvas (XYFlow), the custom step node, Palette, PropertiesPanel, IssuesPanel, SimulationPanel and StructuredEditor (the List view).
  • components/ui/: accessible primitives: Dialog (Radix), Tabs, Toaster with live regions, and ConfirmDialog.

The canvas, the list and the property panel never change the graph themselves. They call the same store actions, which apply the same connection rules. That is what lets the keyboard path and the drag path stay identical in behaviour.

10

Interaction decisions

  • Connections are checked as they are made. While dragging, invalid targets are rejected (self-connections, into Start, or an output that is already used), and the reason is shown in a toast.
  • Undo groups intent, not keystrokes. Rapid typing into one field, or one node drag, becomes a single undo step (changes are merged within 800 ms per field).
  • Errors carry the fix. Messages read “Choose an approver role for ‘Emergency approval’”, appear in the Issues list and on the step itself, and “Show step” jumps to it.
  • Publishing saves first. If validation fails, changes are kept as a draft and the Issues tab opens.
  • Leaving is guarded. React Router’s useBlocker and beforeunload protect unsaved work.
  • Decisions explain themselves. The property panel previews “Requests where Amount (₹) > ₹50,000 follow Yes; all others follow No.” Text fields only allow == and !=.

11

Responsive design

  • 1024px and wider: three columns (palette, design area, 380px side panel), each scrolling independently.
  • 768–1023px: the palette becomes a horizontal row above the canvas, and the side panel moves below.
  • Below 768px: the List view is the default, with Edit and Delete buttons on every step. The canvas stays available as a tab.
  • The minimap only appears at 1280px and wider, so it never covers the workflow on smaller screens.

Automated tests check for horizontal scrolling at 320, 375, 768, 1024, 1440, 1920px, plus a 640px viewport with the root font size at 200%.

12

Accessibility decisions

The target was WCAG 2.1 AA. What I implemented:

  • Skip link, landmarks, one h1 per page, and focus moved to the new heading after client-side navigation.
  • Keyboard alternatives for dragging: Tab to a step, Enter to select it, arrow keys to move it, Delete to remove it. Connections are chosen from labelled selects (“When ‘Approved’, go to…”), and the List view edits everything without the canvas.
  • WAI-ARIA tabs with arrow, Home and End keys, for both the view switcher and the side panel.
  • Dialogs trap focus, start on the first field, close with Escape, and return focus to whatever opened them.
  • Fields have labels, hints and inline errors linked through aria-describedby and aria-invalid.
  • Saves, new connections and each simulation step are announced through polite live regions.
  • Status, severity, outcomes and branch meanings use text and icons, never colour alone.
  • 3px focus rings and contrast-checked tokens in both themes, and transitions disabled under prefers-reduced-motion.

Issues found and fixed during testing

  • axe reported label-content-name-mismatch on the “Open editor” links. Their accessible names now begin with the visible text.
  • A visually hidden label inside the scrolling mobile palette escaped its container and caused horizontal scrolling at 320px. Buttons now create their own positioning context.
  • Dialogs opened from ordinary buttons didn’t return focus on close, so I added explicit focus restoration.
  • The status filter’s accessible names were lowercase because capitalisation was CSS-only. The labels are now real text.

Honest limits: automated checks can’t prove conformance. I tested keyboard use directly and in Playwright, but I haven’t yet tested with NVDA, JAWS or VoiceOver. Dragging an edge on the canvas is pointer-only by nature; the Connections selects and the List view are its equivalents.

13

Technical implementation

  • Stack: React 19, TypeScript, Vite, Tailwind CSS, React Router, XYFlow, Zustand, React Hook Form, Zod, Radix UI, Vitest, Playwright, axe-core, all on current stable releases. TypeScript runs in strict mode with noUncheckedIndexedAccess.
  • Validation is one pure function. It covers start and end rules, broken or duplicate connections, required outputs per step type, required roles, condition types, reachability from Start (a forward search), the ability to reach an End (a reverse search from End steps), and cycle detection that ignores Returned branches.
  • Simulation is a small state machine: startSimulation runs automatic steps until a person must act; act records the action and continues. A 200-step guard stops runaway loops.
  • Theming: semantic CSS custom properties redefined under [data-theme="dark"], mapped into Tailwind and XYFlow variables. An inline head script applies the saved or system theme before first paint, and matchMedia keeps System in sync live.
  • Performance: the editor route, the canvas, the form dialogs and the Zod validator all load on demand, so the workflow list loads about 129 kB of gzipped JavaScript.
  • Import safety: files over 1 MB are refused, and JSON is checked with Zod (types, limits, duplicate ids) before anything is stored.

16

Known limitations

  • Storage is per browser (localStorage). There is no backend, sign-in, sharing or real-time collaboration.
  • Notifications and tasks are simulated; nothing is sent to real people or systems.
  • Branching is exclusive (one path at a time). Parallel approvals (“all of” or “any of”) are not modelled.
  • Roles are a fixed list, and conditions use four request fields with one comparison each.
  • There is no automatic layout. Step positions are manual, and dense workflows can need tidying.
  • Screen-reader testing with real assistive technology has not been done yet.

17

Future improvements

  • An API and database for shared workflows, with authentication and role-based permissions.
  • Parallel branches and join steps; compound conditions (AND/OR).
  • Automatic layout (for example ELK) and alignment guides.
  • A version history with visual diff and rollback between published versions.
  • SLA tracking and escalation paths in simulation.
  • Moderated usability sessions and NVDA/VoiceOver testing to validate the assumptions above.
